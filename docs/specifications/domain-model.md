# Domain model

Status: MVP baseline  
Last reviewed: 2026-07-21

## Purpose

This document defines the business model and rules for the order integration
system. It deliberately does not define HTTP payloads, DynamoDB keys, or exact
event schemas. Those are representations of this model and will be decided in
later steps.

## Modeling principles

- `Order` is the consistency boundary for order state changes.
- Identifiers are opaque values; consumers must not derive meaning from them.
- Money uses integer minor units rather than floating-point arithmetic.
- Time is stored as an instant and serialized in UTC.
- State changes are explicit, validated, versioned, and attributable.
- Delivery and messaging are at-least-once processes, so every external effect
  requires an idempotency rule.
- Only synthetic data is allowed in this learning project.

## Order aggregate

`Order` is the aggregate root. A successful command either leaves the complete
aggregate valid or makes no change.

| Field | Type | Rule |
| --- | --- | --- |
| `orderId` | `OrderId` | Stable platform-generated identifier. |
| `merchantId` | `MerchantId` | Identifies the order owner; one fixed merchant is used in the MVP. |
| `merchantOrderReference` | string | Required and unique within a merchant. |
| `status` | `OrderStatus` | Must follow the state machine below. |
| `items` | `OrderLine[]` | Contains between 1 and 50 lines. |
| `pickup` | `DeliveryLocation` | Synthetic pickup location. |
| `dropoff` | `DeliveryLocation` | Synthetic drop-off location. |
| `provider` | `ProviderAssignment` | Stable provider assignment and references. |
| `failure` | `FailureDetails` or absent | Safe diagnostic context; required only in a failed state. |
| `createdAt` | `Instant` | Set once when the order is created. |
| `updatedAt` | `Instant` | Advances on every successful state change. |
| `version` | positive integer | Starts at 1 and increments on every successful mutation. |

The idempotency key and its request fingerprint are not ordinary order fields.
They belong to a separate idempotency record that points to the created order.

## Value objects

### Order identifiers

- `OrderId` is generated by the platform and exposed as an opaque string.
- `MerchantId` scopes merchant-owned uniqueness and authorization.
- `merchantOrderReference` is supplied by the client for business
  reconciliation. A second order with the same merchant and reference is a
  conflict even if it uses a different idempotency key.

The exact identifier format and length constraints will be defined in the API
contract. Domain code will use distinct TypeScript types so these identifiers
cannot be accidentally interchanged.

### Order line

| Field | Rule |
| --- | --- |
| `itemReference` | Required merchant item reference. |
| `description` | Required synthetic description suitable for display. |
| `quantity` | Integer from 1 through 100. |
| `unitPrice` | Non-negative `Money` value. |

An order total is derived from its lines. It is not accepted as an independent
client-controlled value.

### Money

| Field | Rule |
| --- | --- |
| `amountMinor` | Non-negative safe integer in the currency's minor unit. |
| `currency` | Three-letter ISO 4217 currency code. |

Every line in an order uses the same currency. The MVP does not perform currency
conversion, tax calculation, payment, or settlement.

### Delivery location

| Field | Rule |
| --- | --- |
| `addressLine` | Required synthetic street-level value. |
| `city` | Required synthetic locality. |
| `postalCode` | Required synthetic postal code. |
| `countryCode` | Two-letter ISO 3166-1 country code. |

Real delivery systems would usually require recipient and contact information.
Those values are deliberately absent to prevent this project from handling
personal data.

### Provider assignment

| Field | Rule |
| --- | --- |
| `providerCode` | Stable code identifying the selected provider; fixed to the mock provider in the MVP. |
| `submissionKey` | Stable idempotency token used for every attempt to submit this order. |
| `providerOrderId` | Provider reference; absent until the provider confirms acceptance. |
| `acceptedAt` | Provider acceptance time; absent until acceptance is confirmed. |

`submissionKey` is created with the order and never changes, including after an
operator-approved retry. This protects against the failure in which the provider
accepts a request but the platform loses the response and sends it again.

### Failure details

| Field | Rule |
| --- | --- |
| `stage` | Either `SUBMISSION` or `DELIVERY`. |
| `reasonCode` | Stable internal code suitable for decisions and metrics. |
| `summary` | Safe diagnostic summary without secrets or sensitive provider data. |
| `occurredAt` | UTC instant at which the terminal attempt or delivery failure was recorded. |

`SUBMISSION_FAILED` requires submission-stage failure details, and
`DELIVERY_FAILED` requires delivery-stage failure details. An approved retry
clears the previous submission failure as the order returns to
`PENDING_SUBMISSION`.

## Order status

| Status | Meaning | Terminal |
| --- | --- | --- |
| `PENDING_SUBMISSION` | The platform accepted the order, but provider acceptance is not confirmed. | No |
| `SUBMISSION_FAILED` | Provider acceptance was not confirmed after a permanent failure or exhausted processing. | No |
| `SUBMITTED` | The provider confirmed and returned a provider order reference. | No |
| `PICKED_UP` | The provider reports that delivery is in progress. | No |
| `DELIVERED` | Delivery completed successfully. | Yes |
| `DELIVERY_FAILED` | A provider-accepted delivery ended unsuccessfully. | Yes |
| `CANCELLED` | The order was cancelled before completion. | Yes |

Separating `SUBMISSION_FAILED` from `DELIVERY_FAILED` is important:

- A submission failure can be reviewed and safely retried with the stable
  provider submission key.
- A delivery failure happened after provider acceptance and must not create a
  second provider delivery request.

## State transitions

| Current state | Next state | Authorized source | Additional rule |
| --- | --- | --- | --- |
| New | `PENDING_SUBMISSION` | Create-order command | All order invariants and uniqueness rules pass. |
| `PENDING_SUBMISSION` | `SUBMITTED` | Provider worker or reconciliation | Provider order ID and acceptance time are recorded atomically. |
| `PENDING_SUBMISSION` | `SUBMISSION_FAILED` | Integration workflow | Only after a permanent failure or exhausted retry policy. |
| `PENDING_SUBMISSION` | `CANCELLED` | Authorized operator | Provider acceptance must not already be known. |
| `SUBMISSION_FAILED` | `PENDING_SUBMISSION` | Authorized operator | Recovery reason is required; reuse the existing submission key. |
| `SUBMISSION_FAILED` | `CANCELLED` | Authorized operator | Recovery is intentionally abandoned. |
| `SUBMITTED` | `PICKED_UP` | Provider webhook or operator reconciliation | Provider event is authenticated or the operator supplies a reason. |
| `SUBMITTED` | `DELIVERED` | Provider webhook or operator reconciliation | Permitted when the provider legitimately omits an intermediate pickup event. |
| `SUBMITTED` | `DELIVERY_FAILED` | Provider webhook or operator reconciliation | Failure details are recorded outside the status value. |
| `SUBMITTED` | `CANCELLED` | Provider webhook or operator reconciliation | The provider-side cancellation is confirmed. |
| `PICKED_UP` | `DELIVERED` | Provider webhook or operator reconciliation | Provider event is authenticated or the operator supplies a reason. |
| `PICKED_UP` | `DELIVERY_FAILED` | Provider webhook or operator reconciliation | Failure details are recorded outside the status value. |

No transition is allowed out of `DELIVERED`, `DELIVERY_FAILED`, or `CANCELLED`.
Changing an order to its current status is an idempotent no-op, not a new state
transition. A no-op does not increment the aggregate version.

Automated retries do not repeatedly change the status. The order stays
`PENDING_SUBMISSION` while retryable attempts are in progress.

## Aggregate invariants

1. `merchantId` plus `merchantOrderReference` is unique.
2. The order has at least one valid line and no more than 50 lines.
3. All line prices use the same currency and the total can be calculated using
   safe integer arithmetic.
4. Pickup and drop-off locations are both valid and distinct business values.
5. `createdAt` never changes; `updatedAt` cannot precede it.
6. A successful mutation increments `version` exactly once.
7. `providerCode` and `submissionKey` never change after creation.
8. Entering `SUBMITTED` atomically records `providerOrderId` and `acceptedAt`.
9. `PICKED_UP`, `DELIVERED`, and `DELIVERY_FAILED` require a provider order ID.
10. Failed states contain matching failure details; non-failed states do not
    retain an active failure value.
11. Terminal orders cannot be mutated by later status events.
12. A rejected command or event leaves every aggregate field unchanged.

## Create-order idempotency

An idempotency record contains:

- Merchant scope
- Client-supplied idempotency key
- Canonical fingerprint of the business request
- Created `orderId`
- Creation time

The canonical fingerprint includes the merchant order reference, order lines,
pickup, and drop-off values. It excludes transport details such as request IDs,
headers, and request time.

The rules are:

1. A new key and a unique merchant order reference create exactly one order and
   its idempotency record as one atomic operation.
2. The same key and same fingerprint resolve to the original logical order and
   do not repeat creation side effects.
3. The same key with a different fingerprint is an idempotency conflict.
4. A different key with an existing merchant order reference is a business
   uniqueness conflict.
5. Concurrent requests follow the same rules; only one can create the order.
6. For the MVP, the idempotency record is retained for the lifetime of the order
   environment. It has no independent expiry.

Keeping records for the environment lifetime is intentionally simple and safe
for the small MVP dataset. A production retention policy would require a
business decision about retry windows, storage growth, and legal retention.

## Duplicate event rules

Every domain event must eventually carry:

- A globally unique event ID
- Event type and schema version
- Aggregate ID and aggregate version
- Occurrence time
- Correlation and causation references

Each consumer applies these rules:

1. Deduplicate by consumer identity plus event ID, not by payload similarity.
2. A previously successful event is acknowledged without repeating its state
   change or external side effect.
3. Reuse of an event ID with a different payload is a conflict and operational
   alert.
4. State changes use the expected aggregate version to prevent lost concurrent
   updates.
5. An event that requests a backward or otherwise invalid transition is recorded
   as stale or invalid and leaves the order unchanged.
6. Provider submission retries always reuse `ProviderAssignment.submissionKey`.
7. The mock provider webhook contract must supply a stable provider event ID.
   Webhook authentication and replay-window details will be defined later.

The storage transaction and consumer-specific deduplication representation are
infrastructure decisions, not domain rules.

## Examples

### Successful delivery

1. `CreateOrder` creates order `O1` as `PENDING_SUBMISSION`, version 1.
2. The worker submits `O1` using its stable submission key.
3. `ConfirmProviderSubmission` records provider order `P1`, changes the order to
   `SUBMITTED`, and increments the version to 2.
4. An authenticated provider event changes it to `PICKED_UP`, version 3.
5. A later provider event changes it to `DELIVERED`, version 4.

### Repeated create request

Two concurrent requests contain the same idempotency key and business values.
One creates order `O1`; the other resolves to `O1`. Only one `OrderCreated` fact
is produced.

### Lost provider response and retry

The provider accepts an order, but the worker times out before receiving the
response. The retry uses the same submission key, allowing the provider to
return the original result instead of creating another delivery.

### Invalid terminal transition

An operator or delayed webhook attempts to change a `DELIVERED` order to
`CANCELLED`. The command is rejected, the order remains `DELIVERED`, and its
version does not change.

### Stale provider event

After an order reaches `DELIVERED`, a delayed pickup event with a new event ID
arrives. It is recorded as stale, does not change the order, and does not
increment the version.

### Concurrent status changes

Two status commands both expect version 2. The first valid command succeeds and
creates version 3. The second fails its version condition and must reload the
order before deciding whether its requested transition is still valid.

## Requirements resolved by this model

- Q-001: required business fields are defined by the aggregate and value objects.
- Q-002: statuses, transitions, ownership, and terminal states are defined.
- Q-003: create-order idempotency records remain for the MVP environment
  lifetime.
